# quorra research pipeline

`$QUORRA` = `$HOME/agent-stack/quorra`. Expand `$HOME` to your home folder when a tool needs a full path (the Read, Write and Edit tools do). Substitute this literal path in every command below, because your working directory may be another project, and quote every path. You are the controller of this pipeline: you spawn agents with the Agent tool and never do their work yourself. Each agent returns at most 10 lines; read its output file only when you need a detail.

## 0. Decide the scope (ask the user to confirm)
- `python3 "$QUORRA/scripts/research_tools.py" status` prints a JSON list, one entry per repo. A repo is due when `suggest_rerun` is true. That already covers more than 200 commits since the research commit, a rule refuted during real work, `diverged` (the research commit is no longer an ancestor of the current one), `unknown_sha` and `never_researched`. Treat all three of those flags as due.
- To see what a repo has today: `python3 "$QUORRA/kb/kb.py" list --type convention --repo <repo> --live --json` (rows have `id`, `scope`, `area`, `rule`, `tier`).
- A repo whose index has more than 50,000 symbols (`sqlite3 "$QUORRA/index/<repo>.sqlite" "select count(*) from symbols"`) is researched per module. Take the repo path from `$QUORRA/config/repos.json` (expand `~`), list its top-level source dirs (`git -C "<path>" ls-tree -d --name-only <sha> src/`), group them into 4-8 modules of similar size, and run steps 1-4 once per module with `--path-prefix` (a **module run**). Tooling and reviewer conventions belong to the whole repo, so add one **whole-repo pass** for such a repo; the whole-repo pass runs first, before any module run: steps 1-4 once without `--path-prefix`, spawning only the `tooling` and `reviews` scouts (plus the `testing` scout when the repo keeps its tests outside every module prefix, for example in a top-level `tests/`), with the synthesizer brief "tooling and review pass". Module runs skip the `tooling` and `reviews` scouts and use the synthesizer brief "module run".
- If a repo has no index yet (`$QUORRA/index/<repo>.sqlite` is missing), run `python3 "$QUORRA/scripts/index_repo.py" <repo>` first.
- Tell the user the plan (repos or modules, rough agent count) and wait for yes.

## 1. Prep (script)
```bash
RUN=$(python3 "$QUORRA/scripts/run_record.py" new research-<repo> --type research --request "<the user's words>" --repos <repo>)
python3 "$QUORRA/scripts/prep_repo.py" <repo> --run "$RUN" [--path-prefix <module dir>]
python3 "$QUORRA/scripts/fetch_mr_reviews.py" <repo> --run "$RUN" --limit 100
```
`--path-prefix` is normalised (`./src/Voucher`, `/src/Voucher` and `src/Voucher/` are the same). `$OUT` is `$RUN/<repo>` for a whole repo, or `$RUN/<repo>--<seg>--<seg>` for a module, with the prefix segments joined by `--` (prefix `src/Module/` gives `$RUN/shared-lib--src--Module`). Read `$OUT/prep.json` for `sha`, `sha_date` (the research commit's committer date), `scope` and the `areas` object (area name to file count). In a module run, skip the `"$QUORRA/scripts/fetch_mr_reviews.py"` command: reviews are fetched once, in the whole-repo pass. If `"$QUORRA/scripts/fetch_mr_reviews.py"` prints `"low_evidence": true`, mark the reviews area low-evidence: rules resting only on reviews stay unverified.

## 2. Scouts (parallel, one message)
Spawn one `quorra-scout` per area listed in `prep.json["areas"]`, all in a single message. In a module run, skip the `tooling` and `reviews` scouts; in the whole-repo pass of a repo researched per module, spawn only the `tooling` and `reviews` scouts, plus `testing` when the tests live outside every module prefix (module runs would otherwise report no tests at all). Tell every agent you spawn in parallel to keep its helper files in its own folder, `$OUT/scratch/<agent>-<area or purpose>/`, and to delete it if it is empty when it finishes: parallel agents that shared one scratchpad overwrote each other's files in Task 10. Brief each with the repo, its path, the sha, the area and `$OUT`; for `reviews` add the path `$RUN/<repo>/reviews.jsonl` (that script always writes under the plain repo name, even for a module run). Use the default model (haiku), except for the `reviews` and `data-storage` scouts, which you spawn with `model: "sonnet"`. After each returns, record it: `python3 "$QUORRA/scripts/run_record.py" append "$RUN" subagents '{"name": "quorra-scout", "model": "<m>", "purpose": "<area>", "tokens": <from the Agent result usage>}'`.

## 3. Synthesis
Spawn `quorra-synthesizer` with the repo, path, sha, `$OUT`, run id (`basename "$RUN"`) and scope. For a repo researched per module, add the brief "module run" to each module run (it writes no `source: tooling` or `source: review` rules, but may read tooling to judge tiers) and "tooling and review pass" to the whole-repo pass (it writes only `source: tooling` and `source: review` rules, unscoped, plus unscoped `area: testing` rules with `source: code` when the `testing` scout ran). On a first run it writes `$OUT/rules.json` and ingests it; if it reports that the KB export was refused, stop and tell the user. On a refresh, say in the brief: "write rules.json but do NOT ingest"; the gate is in the Refresh section. Record the subagent with `python3 "$QUORRA/scripts/run_record.py" append "$RUN" subagents '...'`, as in step 2; do the same after every agent in the steps below.

## 4. Verification
```bash
python3 "$QUORRA/scripts/research_tools.py" sample --repo <repo> --run-id <run id>
```
This prints a JSON list of rule ids. Spawn `quorra-verifier` (research mode, round 1) with that list, the repo, path, sha, `$OUT` and run id. It writes `$OUT/verdicts.json` and applies it with `python3 "$QUORRA/kb/ingest_rules.py" verdicts "$OUT/verdicts.json" --run-id <run id> --round 1`; only `sustained` and `refuted` are valid verdicts, and any entries it reports as `skipped` need fixing.

Revision loop for refuted rules:
1. Spawn `quorra-synthesizer` with the refutations (brief: "revision: write rules-revised.json with only the revised versions of these rules, each with `replaces` set to the old id, and list each rule you give up as `{"drop": "<id>", "reason": "..."}`; do not ingest"). It writes `$OUT/rules-revised.json`.
2. Dry-run it first with `python3 "$QUORRA/kb/ingest_rules.py" plan "$OUT/rules-revised.json"` to see which entries change tier, which ids it `supersedes` and which it will `drop`. The file is partial, so `plan` lists every other live rule of the repo under `missing`; that is expected. Never use `--retire-missing` with `rules-revised.json`. Then ingest it yourself: `python3 "$QUORRA/kb/ingest_rules.py" ingest "$OUT/rules-revised.json"`. Ingest pairs each revised rule with the id in its `replaces`: a reworded rule gets a new id and ingest supersedes the old one itself, carrying its refutation over (the output lists these pairs under `superseded`); a rule with the same wording keeps its id and needs nothing, so running `supersede` by hand is never needed (a same-id `supersede` is a harmless no-op). Each `drop` entry is dropped with a lesson (output `dropped`). If the synthesizer left a refuted rule out without a `drop` entry, drop it yourself: `python3 "$QUORRA/kb/ingest_rules.py" drop <id> --run-id <run id> --reason "<the synthesizer's reason>"`. Fix any rule in `rejected` (for example a `replaces` that names an unknown id) and ingest again.
3. Spawn `quorra-verifier` for round 2 with every id in the `ingested` list that this ingest of `rules-revised.json` printed (that covers reworded rules, tier changes and rules revised with the same wording and tier); it writes `$OUT/verdicts-2.json` and applies only that file with `python3 "$QUORRA/kb/ingest_rules.py" verdicts "$OUT/verdicts-2.json" --run-id <run id> --round 2` (never re-apply the round-1 file with `--round 2`). A rule refuted in round 2 (that is, twice in this run) is dropped and becomes a lesson.
4. Rules refuted for the first time in round 2 (for example re-tiered rules that round 1 never sampled) are not dropped, because they were refuted once. Do not start a round 3 of agents: at the review gate show the user each one with the verifier's evidence and a suggested fix (drop, narrow, re-tier or reword). Apply their decisions yourself: `python3 "$QUORRA/kb/ingest_rules.py" drop <id> --run-id <run id> --reason "the user: ..."` for drops, and for the rest write `$OUT/rules-user.json` (each rule with `replaces`), check it with `plan`, ingest it, then mark the ingested ids verified with a `verdicts-user.json` of `sustained` entries (evidence "the user approved at the review gate") applied with `--round 3`.

## 5. Consistency (after all PHP framework repos are done for this run)
Spawn `quorra-consistency` with the run id and the PHP repo list (api-app, admin, pricing, framework, shared-lib, core-app). Open a dedicated run for it first (`python3 "$QUORRA/scripts/run_record.py" new consistency-<date> --type research --request "cross-repo consistency" --repos api-app,admin,pricing,framework,shared-lib,core-app`) and use that run id: it holds `consistency.json` and `contradictions.json`. The agent writes `$QUORRA/runs/<run>/consistency.json` (a bare list of share groups, used by the `share` step of this run's curator) and `$QUORRA/runs/<run>/contradictions.json`. Show the user every entry in `contradictions.json` and ask which instruction holds; record their answer as an exception or a lesson.

## 5b. Concepts (once, not in every repo run)
The concept map is seeded once, in the acceptance run (plan Task 11), not in every repo run. Only when the user or the brief asks for it: after the rules are verified, seed the concept map: `python3 "$QUORRA/scripts/concepts.py" candidates --kb "${QUORRA_FEATURE_KB:-$HOME/feature-knowledge-base}" --out "$RUN/concept-candidates.json"`, draft `$RUN/concepts.json` from the candidates (each concept needs `names` as en/fa/codename lists and implementations with repo, file and symbol), then give that run's curator the steps `concepts, render, close` in step 6, so `concepts` runs before the run is closed.

## 6. Curation
Spawn `quorra-curator` per repo (or module run) with the run id, the run folder and the steps `render, close`, plus `concepts` only when step 5b ran for this run and the brief asks (then `concepts, render, close`); add `lessons` with the user's quotes and `proposals` if a toolkit gap showed up. Per-repo curators never run `share`, because `consistency.json` exists only in the consistency run. After step 5, spawn one more curator for the consistency run with the steps `share, render, close`. The `share` step prints `{"shared": [...], "skipped": [...]}`; relay the skipped groups and why. The `concepts` step runs `python3 "$QUORRA/scripts/concepts.py" verify`, which exits 2 for `no_index` or `invalid` entries: `no_index` mappings must be kept and flagged, never dropped. Every per-repo run is closed by its own curator (`close` step), and so is the consistency run. Then show the user the headline from the rendered `$QUORRA/kb/conventions/<repo>.md`: rule counts per tier (count them from `python3 "$QUORRA/kb/kb.py" list --type convention --repo <repo> --live --json`) and the five most important rules.

## 6b. Held-out MR check (acceptance, plan Task 11)
The cutoff is the research commit's committer date: `sha_date` in `$OUT/prep.json`, the same value as `git -C "<path>" log -1 --format=%cI <sha>`. For a repo researched per module, use the latest `sha_date` among all of that repo's `prep.json` files: the whole-repo pass's `"$QUORRA/runs/<whole-repo run>/<repo>/prep.json"` and every module run's `"$QUORRA/runs/<module run>/<repo>--<seg>--<seg>/prep.json"`. The MRs used during research are in `"$QUORRA/runs/<whole-repo run>/<repo>/reviews.jsonl"` (module runs fetch no reviews). Fetch the MRs merged after the cutoff: `python3 "$QUORRA/scripts/eval_mrs.py" fetch <repo> --after "<sha_date>" --limit 10 --exclude-from "$RUN/<repo>/reviews.jsonl" --out "$RUN/<repo>/heldout"` (for a repo researched per module, `$RUN` here is the whole-repo run), spawn `quorra-verifier` in mr-check mode, then `python3 "$QUORRA/scripts/eval_mrs.py" score "$RUN/mr-labels.jsonl"`. With fewer than 5 held-out MRs, note "not enough new MRs yet" instead of scoring.

## Refresh
A refresh is gated, because ingest applies tier changes at once and would leave rules the refresh no longer finds live.
1. After `python3 "$QUORRA/scripts/run_record.py" new` (step 1) has created `$RUN` and before anything is ingested, snapshot the live rules: `python3 "$QUORRA/scripts/research_tools.py" snapshot --repo <repo> --out "$RUN/<repo>-rules-before.json"`.
2. Run steps 1-2, then step 3 with the refresh brief (the synthesizer writes `$OUT/rules.json` and does not ingest).
3. Dry run: `python3 "$QUORRA/kb/ingest_rules.py" plan "$OUT/rules.json"`. It prints `new`, `tier_changed`, `revived` (retired or dropped rules the refresh found again), `unchanged`, `unchanged_via_rewording` (the file has the old wording of a rule that was reworded; its replacement stays live), `missing` and `rejected`, and writes nothing. It compares only rules of the same repo and scope. Show the user all of them and ask the user to confirm the tier changes, the revived rules and the missing rules (spec section 8: tier changes are proposed, then confirmed).
4. Only after the user says yes: `python3 "$QUORRA/kb/ingest_rules.py" ingest "$OUT/rules.json" --retire-missing`. Rules whose wording and tier are unchanged keep their verified flag; tier changes and new rules start unverified; missing rules are retired.
5. Continue with step 4 (verification) and the rest. To see the net effect afterwards: `python3 "$QUORRA/scripts/research_tools.py" diff --repo <repo> --before "$RUN/<repo>-rules-before.json"`.

## Safety
Only these read commands are allowed in the clones: show, grep, log, ls-tree, cat-file, diff, rev-parse, rev-list at a sha, and fetch through `python3 "$QUORRA/scripts/index_repo.py" <repo> --fetch`; anything else is forbidden. GitLab GET only. Never print or write a secret value. Copied tooling, guides, reviews and held-out diffs stay in the run folder and are gitignored.
