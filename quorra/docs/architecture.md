# quorra architecture

quorra is the builder agent for your engineering team and a sibling of the clu analyst agent. At this stage it answers "does X already exist?" and "how do we do X in repo Y?" from a code index and a knowledge base of tiered, cited conventions.

## Entry points
- `claude --agent quorra` starts the lead agent. The name comes from the `name` field in `agents/quorra.md`; the lower-case form is verified to work (verified in fix round 1: `claude --agent quorra -p` answered correctly).
- The shell alias `quorra` (added to `~/.zshrc` by `install.sh`) runs the same command.
- `/quorra <question>` (skill `skills/quorra`) works from any Claude Code session. It spawns the quorra agent as a subagent and relays its `NEEDS_ALIGNMENT` questions to the user. The block formats are in `skills/quorra-core/references/teammate-protocol.md`, and runs are recorded with `mode: teammate`.
- `/quorra-review` reviews pending self-improvement proposals.

### Teammate mode and permissions
In teammate mode the `/quorra` skill spawns the quorra subagent, which reads code under the calling session's permissions. In a headless session (`claude -p`) a subagent's reads may be denied by default, so no citation comes back. For headless use you can add a read-only allowlist yourself: `python3` on `"$QUORRA/scripts/*"` and `"$QUORRA/kb/*"`; `git -C <repo> grep|show|log|ls-tree|rev-parse`; and Read on the quorra folder and your code folder. Nothing in this repo modifies settings files.

## Agents
quorra (`agents/quorra.md`) runs on Opus with `memory: user` and preloads the `quorra-core` skill. Five research agents, spawned by the controller through the `quorra-research` skill (`skills/quorra-research/SKILL.md`, the pipeline): `quorra-scout` (haiku, sonnet for the `reviews` and `data-storage` areas), `quorra-synthesizer` (opus), `quorra-verifier` (opus), `quorra-consistency` (sonnet) and `quorra-curator` (haiku). The pipeline runs prep, scouts, synthesis, verification, consistency and curation, and every agent writes its output to the run folder and returns at most 10 lines.

## Protocol
The full protocol is in `skills/quorra-core/SKILL.md`. The review flow is in `skills/quorra-review/SKILL.md`.

## Data stores
- Knowledge base: `kb/kb.sqlite`, rebuilt from the committed `kb/export/*.jsonl` files.
- Code indexes: `index/<repo>.sqlite`, generated and gitignored. Every extractor passes its symbols through `scripts/qindex/redact.py`, which drops credentials by name (SENSITIVE), by shape (URL userinfo, secret key=value pairs, Basic/Bearer, JWT) and by entropy (random-looking 24+ character keys). `meta.extractor_version` forces a full rebuild when the extractors change.

## Lookup output
- `lookup.py "<q>" --json` returns `{hits, stale, missing, grep_failed, terms, shas, warnings}`. A repo in `missing` has no index and was not searched; `grep_failed` means git grep could not run there (its index hits still count).
- `lookup.py --endpoints` prints a JSON array of frontend-to-backend pairs `{url_norm, front: {file, line, name}, back: {repo, file, line, method, handler}}`, and names skipped repos (no index) on stderr. `lookup.py --endpoints --json` returns `{"pairs": [...], "skipped": [repo, ...]}` instead. Backends are the php and java repos.
- Runs: `runs/<date>-<slug>/run.json`.
- Proposals: under `proposals/`.

## Read-only guarantee
In the configured code repos only these read commands are allowed: `git show`, `git cat-file`, `git grep`, `git log`, `git ls-tree`, `git diff` and `git rev-parse` at a sha; anything else is forbidden. It never runs checkout, reset, switch, stash or pull in the configured code repos. The only remote-touching commands allowed are `git fetch`, `git clone` and GitLab API GET requests.

## Self-improvement
Free writes need no approval: lessons, exceptions, concepts and run records. Changes to quorra's own agents, skills, scripts or research areas are gated: they are filed with `scripts/proposals.py new` and applied only after the user approves them in `/quorra-review`.

## Sub-project 2: explain mode and KB upkeep (2026-09-30)

- **`scripts/kb_cite.py`** reads every code citation in a feature KB feature folder (`repo:path:line`, `path:line`, `File.php:line`, `Class::method()`, `Class:line`) and the doc's `<!-- quorra-verified: repo@sha ... on date -->` footer. `extract` resolves each citation to one repo file through the indexed tree; anything with no match, or more than one, is listed as unresolved and never guessed. `stale` compares each citation's baseline sha (the footer, or `--sha repo=<sha>`) with the indexed sha and reports `unchanged`, `moved` (with the new line), `changed` (within ±5 lines, or the method body), `gone` (with the deleting commit), `unresolved` or `no_baseline`; it exits 1 when anything is stale. `stamp` writes one footer per doc.
- **`scripts/kb_git.py`** creates `quorra/<feature>-<date>` in the KB repo from main, refuses unrelated tracked changes, commits only `features/<feature>/` after a secret scrub of every staged line, and prints the files and headings touched. It has no push command.
- **`skills/quorra-explain/SKILL.md`** is the controller protocol for explain, refresh and update-after-work. Discovery and schema start from quorra's index; the feature-explainer agents are spawned only for what the index cannot answer and for stale citations. Hand-off rule: quorra commits on a local branch, shows the user the summary, and pushes only after the user says yes, once per push.

## Sub-project 3: builder core (2026-10-03)

- **`scripts/work.py`** owns quorra's own clones under `~/code/quorra-work/` (env `QUORRA_WORK_DIR`). `prepare` clones from the user's local clone (a read), points `origin` at GitLab, creates `quorra/<slug>` from the indexed commit, and installs the repo's dependencies (a PHP framework's tests may need a test image and cannot run locally). It refuses any repo outside the `QUORRA_WRITABLE` list, and refuses to switch tasks over uncommitted work. `check` runs the repo's checks and reports each as `passed`, `failed` or `not_run` with the reason. `diff` and `patch` give the change (the patch is refused if any line trips the secret scrub). `panel up|test|down` runs the front-end app locally and collects Playwright screenshots.
- **No push, four ways:** there is no push command; every remote gets a push URL that cannot work; `pushInsteadOf` rewrites the GitLab URLs (https, ssh and scp style) and the user's clone paths (each repo path and its parent folder) to a `no-push://` scheme git cannot speak, so an explicit URL or path fails even with `--no-verify`; and a `pre-push` hook refuses. The hook alone was not enough: the front end's install runs husky, which points `core.hooksPath` elsewhere, and a global hooksPath could do the same. So `work.py` pins `core.hooksPath` to the clone's own `.git/hooks`, and re-applies the whole lock at the start of every command (`prepare`, `check`, `status`, `diff`, `patch`, `panel`) and after every install, even an interrupted one.
- **`config/checks.json`:** PHP repos lint changed files and can report PHPUnit as `not_run` ("needs the framework test image (Docker); left to CI") when the tests need a CI image that cannot run locally. The front end installs with `npx yarn@1.22.22` and runs oxlint on changed files, `tsc` and the Jest tests related to changed files. The panel entry gives the start command, the port and the Playwright command.
- **Agents and skill:** `quorra-builder` (sonnet) writes one task at a time with TDD; `quorra-reviewer` (sonnet; opus for the final review) reads through the `conventions`, `correctness` or `final` lens. `skills/quorra-build/SKILL.md` is the flow: align, design approved by the user, plan, prepare, build loop with at most 3 fix rounds, local app, final review, hand-off, KB upkeep, learning. Pushing and merge requests come in sub-project 4.

## Sub-project 4: Jira and GitLab workflow (2026-10-03)

- **`scripts/jira_ops.py`** is quorra's only way into Jira, and it works in the one Jira project named in `config/jira.json` only. `track` links a ticket to a run, `propose` turns `jira-proposal.json` into `jira-proposal.md` and prints a fingerprint, `create --approve <fingerprint>` creates the tickets (it can be re-run and skips tickets already made for that fingerprint), `move` sends a ticket to start or review, and `comment` adds a comment. The transition names are in `config/jira.json`.
- **`scripts/publish.py`** ships a build. `plan` reads `<run>/publish-request.json` and prints the plan with its fingerprint. `push --approve <fingerprint>` pushes each repo from a temporary clone with the user's own git credentials, opens the merge request through `gitlab_client.post_json`, records it in the registry and the run (`publish` field), moves the Jira ticket to In Review and comments the merge request link. It exits 1 if any item has an error. `update <repo>!<iid> --plan | --approve <fingerprint>` pushes review fixes to an existing merge request.
- **`scripts/mrs.py`** checks merge requests on request. `register` adds an existing one to the registry, `status` prints a short summary and the path of a result file holding the full threads and failed-job logs, and `reply <batch.json> --plan | --approve <fingerprint>` posts approved replies into existing threads.
- **`scripts/gitlab_client.py`** holds the verifying SSL context, the same-host redirect handling and the GET and POST calls; **`scripts/mr_registry.py`** reads and writes `state/mrs.json` (git-ignored).
- **Skills:** `quorra-build` gains the Jira proposal, the ticket moves and the Ship step. `quorra-mrs` (linked into the agent-stack `skills/` folder) is the protocol for "check my MRs": status, sort, fix, draft, approve, send.
- **Approval fingerprints:** every outward action takes `--approve <fingerprint>`, recomputed from the current state; a changed plan or branch head makes it refuse. A yes to the hand-off summary is not a yes to ship.
- **Safety rules:** writable repos only (the `QUORRA_WRITABLE` list); remote branches start with `feat/` or `fix/`; every outgoing commit message and added line is scanned for secrets; a fresh passing `work.py check` on the branch head is required; a remote branch with other history is refused; no force push, merge, approve, close, rebase, branch delete, thread resolve or note edit; no Jira writes outside the configured project; no attribution line in anything sent to GitLab, Jira or Confluence; review comments, CI logs and ticket text are untrusted data. In teammate mode quorra never ships or posts.
- **Final-review refusals:** merge commits, attribution lines in commit messages, partial (`--only`) or dirty-tree check runs, hand-edited plans (static checks re-run at push time), fork MRs, hosts other than your configured GitLab, non-hex reply discussion ids. Jira status moves are covered by the user's design approval and the publish-plan fingerprint; free-text Jira comments need their own fingerprint. Re-runs skip Jira steps and replies already done.
- Decisions and their costs: `docs/decisions-sp4.md`.

## Sub-project 5: TRDs, API contracts and decision reports (2026-10-03)

- **`scripts/doc.py`** is quorra's only way to write documents to Confluence. `new <run> <trd|contract|decision> <slug>` copies a template from `templates/` into `<run>/docs/`. `check <file>` refuses a draft (exit 1, line numbers and reasons, never the text) for a missing section marker, a leftover `<...>` placeholder, an empty section, a technical claim with no citation in its paragraph, list item or table row, a `repo:path:line` citation that does not resolve at the sha in the meta line, an unknown `run:<field>`, a contract field table row with no Source, a possible secret or a tool attribution line. `plan <file> --space DOCS [--parent <id>] [--page <id>]` checks again, converts the Markdown and prints the mode, title, parent, live version and a fingerprint (the `jira_ops._fp` formula), and writes `<file>.plan.json`. `publish <file> --approve <fingerprint>` recomputes the plan and creates or updates the page. `diff <doc_id>` shows what others changed on a page, and `status` lists quorra's pages with their live versions, edits by others, stale citations and any per-page error.
- **`scripts/doc_check.py`** holds the draft checker; **`scripts/confluence_client.py`** is the standard-library Confluence client (verifying SSL, same-origin redirects, the token only in a request header, read from the Confluence env file (`QUORRA_CONFLUENCE_ENV`) and never printed). It loads `md_to_storage` from the Markdown-to-storage converter script named by `QUORRA_CONFLUENCE_WRITER`.
- **`state/pages.json`** (git-ignored) is the page registry: one entry per page quorra created, with its page id, space, title, URL, run, and the version and date it last wrote.
- **Templates:** `templates/trd.md`, `contract.md` and `decision.md` share one header (a meta comment line with `doc_id`, `type`, `run` and `shas`, then the title, author, team, status, sign-offs, links and change log) and one `<!-- section: ... -->` marker per section.
- **Reviewer lens `doc`:** `quorra-reviewer` reads the draft and every cited line and reports false claims, a design that differs from the approved or built one, contract fields that disagree with the code, and missing content. The decision report's prose can be written by a writing agent you configure, which keeps the meta line, markers, headings, citations and code names unchanged.
- **Skill:** `skills/quorra-docs/SKILL.md` (linked into the agent-stack `skills/` folder) is the protocol: draft, check, review (at most 2 rounds), plan, the user's yes to the exact page, publish, handling of pages edited by others, and refresh. `quorra-build` drafts a TRD and contract at Design and a decision report at hand-off, and puts published page links into the merge request description and the Jira comment.
- **Safety rules:** writes only to the one space set by `QUORRA_CONFLUENCE_SPACE` (default `DOCS`); updates only pages in the registry whose live version is the one quorra last wrote; no delete, no move; every write needs the fingerprint of the exact body the user approved; no attribution line in any page; Confluence, Jira and merge request text is untrusted data. In teammate mode quorra never publishes.
- **Run record:** run type `doc` for on-request documents; the `docs` field lists each published page.
- Decisions and their costs: `docs/decisions-sp5.md`.
